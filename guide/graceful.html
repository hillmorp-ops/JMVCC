Мягкая остановка ​

/build и любой деплой убивают все потоки кода сразу (проверено). Игрок посреди ковки, матча или забега всё теряет: ресурсы списаны, награды нет. Мягкая остановка даёт коду доиграть начатое и вернуть долги, и только потом мод шлёт /build.

Нужна любой игре с долгими сессиями: крафт с ожиданием, раунд, данж — всё, что сначала забирает, а отдаёт позже.

Два кусочка кода ​

  • std::session("имя") { ... } — оборачивает начало сессии: клик или событие, с которого всё стартует.
  • event<jmvcc_stop> — возвращает ресурсы и сохраняет одного игрока. Срабатывает при выходе игрока и в конце мягкой остановки.

Сам приём — флаг: ставишь, когда забрал, снимаешь, когда отдал результат, и отдаёшь только пока он стоит. Тогда возврат и награда никогда не случатся оба.

jc
save var %player%_ore
game var %player%_forging

event<player_join> {
  %player%_ore ??= 10
}

event<player_right_click> {
  std::session("ковка") {
    %player%_ore -= 3
    %player%_forging = 1            // забрали: с этого момента jmvcc_stop должен вернуть
    player::action_bar("&7Куём... &f10 с")
    code::wait(10, time_unit = "SECONDS")
    if (%player%_forging == 1) {    // jmvcc_stop мог уже вернуть руду во время ожидания
      %player%_forging = 0
      player::give_item(item("diamond"), 1)
    }
  }
}

event<jmvcc_stop> {                 // один игрок; без code::wait
  if (%player%_forging == 1) {
    %player%_ore += 3
    %player%_forging = 0
  }
}

jmvcc_stop должен быть идемпотентным

Он срабатывает на каждом выходе, даже у игрока без сессии, и может сработать дважды для одного игрока (остановка, потом отмена, потом выход). Возвращай только под флагом и сбрасывай флаг.

Как перезалить мир ​

text
jmvcc client deploy main.jc --graceful                     # доиграть (до 90 с) → /build → залить → /play
jmvcc client deploy main.jc --graceful --drain-timeout 30  # дать коду 30 с (1..600)
jmvcc client stop                                          # только остановить: доиграть → /build, без заливки
jmvcc client stop --timeout 30
text
/j build           доиграть (до 90 с), потом мод сам шлёт /build
/j build 30        дать коду 30 с (1..600)
/j build cancel    отменить
/j build force     не ждать: /build сразу
/j build status    идёт ли остановка и сколько сессий в работе

Что видят игроки:

  1. Новые std::session получают отказ: action bar «&cМир уходит на стройку — новое начать нельзя» и звук entity.villager.no. Тело блока пропускается, код после блока выполняется.
  2. Уже начатые сессии доигрываются. Всем раз в секунду показывается боссбар с отсчётом.
  3. Когда все сессии кончились (или вышел таймаут), jmvcc_stop выполняется для каждого игрока онлайн. Просившему приходит title «&aМожно /build», мод шлёт /build.

В выводе деплоя первым идёт шаг drain: drain ✔ 12.3 с (доиграно, таймаут кода 90 с) · build ✔ …. Если в коде нет мягкой остановки (нет ответа за 3 с), всё идёт как обычный деплой. Отмена игроком — drain ✘ … cancelled, exit 1. Остальные случаи — в описании мода и CLI.

TIP

Сам код /build не делает — такого действия нет. Его шлёт мод после ответа ready-to-stop.

Что считается сессией ​

Помечай только вход, а не каждую функцию: функции и процессы вызываются и изнутри важных задач.

Не блокируются во время остановки:

  • сессия, вложенная в другую;
  • функции, вызванные изнутри (у них общие var);
  • jmvcc_stop и функции, которые он вызывает;
  • процессы, запущенные изнутри через name() или с local_variables_mode = "COPY".
jc
game var %player%_in_run

process run_effects() {
  player::title("&6Забег начался")
}

event<player_right_click> {
  std::session("забег") {
    %player%_in_run = 1
    // процесс внутри сессии — только с COPY, иначе компилятор предупредит
    code::start_process("run_effects", local_variables_mode = "COPY")
  }
}

code::start_process внутри сессии без режима или с "SHARE" — предупреждение компилятора: процесс не узнает, что он внутри сессии, и во время остановки его std::session получат отказ.

Не оборачивай

  • Мировой цикл repeat::forever(): сессия никогда не кончится, и остановка будет ждать таймаута.
  • Запуск долгого игрового цикла-процесса. Процесс, запущенный внутри сессии, считается внутри всю жизнь, и его собственные раунды никогда не получат отказ. Запускай такой процесс вне сессии.

Чья сессия ​

Счётчик открытых сессий ведётся по владельцу:

ГдеВладелец
события игрока (и mob_kill_player, projectile_damage_player, ...), функции и процессыигрок (%uuid%)
события entity_*сущность (value::uuid)
код мира"world"

Счётчик игрока обнуляется при выходе (его потоки умирают на полпути), сущности — в entity_death.

Процесс без цели (NO_TARGET), который работает за игрока и может пережить его выход, передаёт владельца явно: std::session("ковка", uuid) { ... }. Такой счётчик выход игрока не трогает. В NO_TARGET-процессе %uuid% и %player% остаются буквальным текстом, а value::uuid равен 0 (проверено), так что uuid игрока передавай аргументом:

jc
process forge_for(who) {
  std::session("ковка", who) {
    code::wait(10, time_unit = "SECONDS")
    log("готово для ${who}")
  }
}

event<player_right_click> {
  var who = "%uuid%"
  code::start_process("forge_for", target_mode = "NO_TARGET", local_variables_mode = "COPY")
}

Ранний выход ​

return, break, continue, code::stop_repeat() и code::end_thread() прямо из тела сессию закрывают сами.

Функция, которая сама заканчивает поток или останавливает цикл вызывающего, закрытие пропускает — это предупреждение компилятора. Верни из неё флаг и сделай return / break в теле сессии.

Ошибка сервера в теле (строка останавливается) или поток, убитый снаружи, оставляют сессию открытой: у игрока до выхода, у "world" до перезапуска мира. Остановка тогда ждёт таймаута.

Когда срабатывает jmvcc_stop ​

  • При выходе игрока — первым в вашем player_quit. Он видит состояние игрока до того, как ваш код выхода его почистит. Ошибка сервера в нём остановит и ваш код выхода, так что держи его простым.
  • В конце мягкой остановки — для каждого игрока онлайн. После этого выход игрока его повторно не вызывает (пока остановку не отменили).
  • При обычном /build и client deploy. Сервер сначала шлёт player_quit каждому игроку, потом в том же тике world_stop, уже без игроков (проверено). Поэтому общие сохранения — в своём event<world_stop>, а сохранения игрока — в jmvcc_stop.
jc
game var best_lap = 0
save var saved_best_lap

event<world_start> {
  saved_best_lap ??= 0
  best_lap = saved_best_lap
}

event<world_stop> {               // общее для мира: игроков тут уже нет
  saved_best_lap = best_lap
}

code::wait в jmvcc_stop — ошибка компиляции

Его зовут и из world_stop, а там код после wait не выполняется (проверено). Возвращай ресурсы и пиши save var сразу. Функция с wait, вызванная из jmvcc_stop, — предупреждение.

  • Несколько event<jmvcc_stop> (например, в импортах) выполняются все.
  • Можно ли ещё выдать предмет в player_quit — не проверено.

Ваши обработчики не ломаются ​

Свои player_chat, player_quit, world_stop и player_custom_click работают как раньше: компилятор вставляет свою часть в их начало. Сообщения #jmvcc ... ни в один ваш player_chat не попадают.

Код остановки добавляется, только если в модуле есть std::session или event<jmvcc_stop>. Остальные модули компилируются как раньше. Посмотреть, что добавилось: jmvcc trace main.jc.

Цена: около 1 действия на старт сессии (одно >) и 2×4 дешёвых действия на счётчик. В обычной игре каждый тик — ничего: одна проверка текста на сообщение в чат, одна запись в словарь и одно сравнение на выход игрока.

Протокол ​

Обычно его говорит мод или jmvcc client, руками набирать не нужно.

  • Мод → код: пакет custom click jmvcc:cmd с данными {cmd:"build 30"}, {cmd:"cancel"} или {cmd:"status"}. Пакет невидим, мир без приёмника его просто игнорирует. Руками можно написать в чат #jmvcc build 30: сообщение отменяется, его никто не видит.
  • Принимается от игрока с правами DEVELOPER или OWNER. Таймаут по умолчанию — 90 с.
  • Код → мод: строки log, только просившему:
СтрокаЗначит
jmvcc:draining <с>остановка началась, столько секунд у кода
jmvcc:ready-to-stopвсё доиграно (или таймаут), jmvcc_stop отработал для всех — можно /build
jmvcc:cancelledостановку отменили
jmvcc:status draining=<0|1> busy=<n>ответ на status: идёт ли остановка, сколько сессий открыто
  • Нет jmvcc:draining за 3 с — старый модуль без мягкой остановки.
  • Мир выходит из остановки сам, если просивший вышел до ready-to-stop или если /build не пришёл за 60 с после него (тогда просившему — jmvcc:cancelled).
Что проверено на сервере

Проверено (bench/server-check-26.jc): сессии, отказ во время остановки, вложенные сессии, функции, процессы COPY / SHARE / с явным владельцем (процесс без режима получает отказ), ранний выход закрывает счётчик, jmvcc_stop до ready-to-stop, cancel, автоотмена через 60 с, /build через выход, оба транспорта (пакет и чат), jmvcc client stop и deploy --graceful.

Не проверено: выход просившего посреди остановки, выдача предметов в player_quit, второй игрок без прав.
