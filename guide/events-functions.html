События, функции и процессы ​

Код JustMC всегда кто-то запускает: игрок вошёл, кликнул, моб умер, мир стартовал. В JustCode это event<...>. Всё остальное (функции, процессы, циклы) работает внутри событий.

События ​

jc
event<player_join> {
  player::message("Привет, %player%!")
}

event<player_death> {
  line var who = "%player%"          // имя сохраняем заранее, см. ниже
  player::message<all_players>("&c$who &7погиб")
}

%player% внутри текста с <all_players> — открытый вопрос: может подставиться имя каждого получателя. Поэтому имя сначала кладут в line var, а в тексте пишут $who.

  • Полный список — в справочнике событий. Искать по смыслу: jmvcc search смерть.
  • Что доступно в событии (кто участвует, плейсхолдеры, селекторы, какие value:: заполнены): jmvcc sig player_kill_player.
  • return в событии завершает его.

Код вне событий — это world_start ​

Всё, что написано на верхнем уровне файла, попадает в событие запуска мира. Игроков там ещё нет, поэтому сообщение оттуда никто не увидит: log() в world_start теряется. Здороваться — в player_join.

При /play порядок такой: сначала мировой код, потом player_join. Значит, player_join уже видит game var, которые задал мировой код.

player_join приходит и тем, кто уже в мире

Если игрок стоял в мире, когда запустили игру (/play, jmvcc client deploy), player_join для него всё равно сработает. Инициализацию игрока смело кладите туда.

События от действий идут сразу ​

Если действие вызывает событие (например, player::damage → player_take_damage), обработчик выполняется синхронно, до возврата из действия. Сразу после player::damage(1) всё, что записал обработчик, уже видно.

Функции ​

jc
function reward_for(streak) {
  if (streak >= 10) { return 50 }
  if (streak >= 3) { return 20 }
  return 5
}

function sq(x) { return x * x }

event<player_join> {
  var coins = reward_for(4)
  var d = sq(3) + sq(4)
  player::message("Монет: $coins, сумма квадратов: $d")
}
  • Функцию можно звать до её объявления.
  • return выходит только из функции, код после вызова идёт дальше. return без значения — просто выход.
  • Пишите return на каждом пути, иначе вернётся старое значение с прошлого вызова.
  • Функция-условие возвращает 1/0 и работает прямо в if. В repeat::while сравнивайте явно:
jc
function is_top(n) { return n > 5 }

event<player_join> {
  var score = 7
  var i = 0
  if (is_top(score)) { player::message("Ты в топе") }
  repeat::while(is_top(i) == 0) { i++ }
}

Типы параметров ​

Тип параметра пишется через двоеточие: number, text, list, map, vector, location, item или свой enum. В JSON он ничего не добавляет: по типу компилятор выбирает действие понятного имени (m.length() у словаря — размер, m[k] — ключ словаря) и проверяет вызовы.

jc
function total(prices: map, name: text) {
  var n = prices.length()          // get_map_size: m — словарь
  var p = prices[name]             // ключ словаря
  player::message("${name.length()} букв, позиций $n, цена $p")
}

event<player_join> {
  var prices = variable::create_map_from_values(["хлеб", "меч"], [5, 40])
  total(prices, "меч")
}
  • Вызов с явно другим видом — ошибка компиляции у аргумента: total([1, 2], "меч") → «параметр prices — словарь (prices: map), а [1, 2] — список» (param-kind-mismatch).
  • string, int, array, dict работают с предупреждением (каноничные — text, number, list, map). Логического типа нет: true / false — это 1 / 0, пишите number.
  • Тип — только у параметров. У переменной вид — это её значение: var l = [].

Без типа компилятор смотрит все вызовы функции (в файле и в импортах, и через другую функцию: g(y) { f(y) }):

  • везде один вид — берёт его молча, JSON как с типом;
  • виды разные — ставит проверку вида на сервере (variable::is_type: два вида — одна проверка, три — две; стоящие подряд методы одного параметра делят одну) и предупреждает kind-mixed. Если это случайность — поправьте вызов или укажите тип;
  • вид, у которого нет такого действия (f("abc"), а в f — x.sort()), — ошибка у вызова;
  • вызовов нет — список и kind-guessed.

Так же работают проверки (if (x.contains(v)): разные виды — флаг и одна проверка вида перед if), цепочки (x.slice(0, 2).length() — вид результата по веткам) и параметры с типом: f(m: map), вызванная как g(y) { f(y) }, проверяется по вызовам g — g([1, 2]) даст param-kind-mismatch.

jc
function count(x) {
  return x.length()        // вызовы со списком и текстом: if is_type(x, ARRAY) { … } else { … }
}

event<player_join> {
  var a = count([1, 2, 3])   // 3
  var b = count("hello")     // 5
  player::message("$a $b")
}

Результат функции тоже знает вид — по её return: var r = make_list(); r.length() — длина списка. Вызовы по имени-тексту (code::call_function("f")) и значения циклов ({ i, v -> v.length() }) компилятор не видит — там пишите тип или серверное имя. Проверено на сервере (server-check-32, -33): список — ARRAY, словарь — MAP, текст (и "5") — TEXT, неприсвоенная — NUMBER; проверка вида в рантайме даёт верные длины, сортировку и set у списка и у словаря.

Функция делит var с вызывающим ​

Это главная ловушка. Локальная var живёт в потоке, и вызванная функция видит и меняет её, параметры тоже. Черновые значения внутри функции держите в line var: она живёт только в своей строке кода и никуда не передаётся.

jc
function count_to(n) {
  line var i = 0          // своя, вызывающий её не видит
  repeat::while(i < n) { i++ }
  return i
}

event<player_join> {
  var i = 100
  var got = count_to(3)
  player::message("i всё ещё $i, функция дошла до $got")
}

Ещё два следствия:

  • Передали переменную f(coins) — то, что f сделала с параметром, скопируется обратно в coins. Если f сама пишет в coins напрямую, побеждает её запись.
  • Рекурсия, чей результат используется (return fib(n - 1) + fib(n - 2)), считает неверно: все вызовы делят одни локальные. Компилятор предупреждает.

Что ещё проверено на сервере ​

СитуацияЧто будет
В функции есть code::waitвызывающий ждёт, пока она закончит
Ошибка сервера внутри функцииобрывается и строка вызывающего: код после вызова не выполнится
code::stop_repeat() в функции, вызванной из циклаостанавливает цикл вызывающего
break вне цикла в функцииобрывает всю строку события, не только функцию (компилятор предупреждает). Выходите через return
Две функции с одним именемвызов выполняет обе по порядку (предупреждение duplicate-function)

Не дробите событие на функции только потому, что оно длинное: лимита в 43 блока больше нет, сервер выполнил строку из 1002 блоков. Вызов стоит действий и делит var. Функции нужны для повторов и читаемости.

Процессы ​

Процесс — код, который идёт параллельно, своим потоком. Значение он не возвращает.

jc
process wave(n) {
  repeat::times(n) { i ->
    player::message("&eВолна $i")
    code::wait(1, time_unit = "SECONDS")
  }
}

event<player_join> {
  wave(3)                     // процесс идёт сам, событие не ждёт
  player::message("Волны пошли")
}

Вызов wave(3) компилируется в code::start_process с целью «текущий игрок» и копией локальных переменных. Процесс выполняется сразу, в том же тике, до своего первого code::wait.

Цель процесса ​

target_modeКто цельКогда брать
CURRENT_TARGET (так работает name())игрок/сущность событияработа для одного игрока
NO_TARGETниктоцикл на весь мир, который переживёт выход игрока
FOR_EACH_IN_SELECTIONкаждый из выбранных select::...прочитать value:: у каждого выбранного
jc
process world_tick() {
  repeat::forever() {
    player::action_bar<all_players>("&7Игроков: ${value::players}")
    code::wait(1, time_unit = "SECONDS")
  }
}

event<player_join> {
  code::start_process("world_tick", target_mode = "NO_TARGET")
}

В NO_TARGET нет игрока

В процессе без цели %player% и %uuid% остаются текстом (не подставляются), а value::uuid = 0. Нужно имя или uuid игрока — запишите его в переменную до запуска и передайте с local_variables_mode = "COPY". Действия без <селектора> там идут тем, кого выбрали через select::....

Пример выше запустит новый мировой цикл при каждом входе игрока. Один цикл на мир проще всего поставить в верхний код файла (это world_start): см. мини-игру с раундами.

Локальные переменные процесса ​

local_variables_modeЧто видит процессПроверено
COPY (так работает name())копию var вызывающегода
SHAREте же var: запись в процессе видна вызывающемуда
DONT_COPY (по умолчанию у code::start_process)ничего: все var пустые (0)да
jc
process greet() {
  var gift                    // объявление без значения: переменную задаёт вызывающий
  player::message("Мне передали: $gift")
}

event<player_join> {
  var gift = "алмаз"
  code::start_process("greet", local_variables_mode = "COPY")      // «Мне передали: алмаз»
  code::start_process("greet")                                     // DONT_COPY: «Мне передали: 0»
}

Аргументы процесса — это тоже локальные переменные: wave(3) просто пишет n = 3 и запускает процесс с COPY.

Рискованное — в процесс

Процесс, скорее всего, — отдельная строка кода. Тогда ошибка сервера в нём (неверный тип, угаданный аргумент) оборвёт только этот процесс, а не цикл, который его запустил. Это вывод, вживую не проверялось; проверено только, что ошибка обрывает свою строку и строку того, кто вызвал функцию.

Циклы и лямбды ​

Циклы — это действия repeat::. Ключевых слов while и for в языке нет.

jc
event<player_join> {
  var a = 0
  repeat::while(a < 10) { a++ }

  repeat::on_range(0, 4) { i ->
    player::message("шаг $i")          // 0 1 2 3 4: конец включён
  }

  var scores = [10, 20, 30]
  repeat::for_each_in_list(scores) { index, value ->
    player::message("$index: $value")
  }

  repeat::times(3) { i ->
    player::message("раз $i")
  }
}
  • Переменные цикла пишутся стрелкой: { i -> ... }, { index, value -> ... }. Без стрелки блок — просто тело.
  • Что передаёт каждый цикл, видно в справочнике repeat::.
  • break выходит из цикла, continue переходит к следующему шагу. Срабатывают сразу: код после них в этом шаге не выполняется.
  • repeat::on_range(1, n) читает n один раз: если n поменять в теле, шагов не прибавится.
  • Не меняйте список, по которому идёт for_each_in_list: цикл молча оборвётся после текущего шага. Изменения собирайте в другой список (компилятор предупреждает loop-list-modified).
  • В repeat::forever() всегда ставьте code::wait: цикл без паузы съест CPU мира, а долгая нагрузка выше 100% роняет код мира (high_cpu).

code::controller_async_run не работает

Сервер отвечает ошибкой «Action should not be executed directly» и обрывает строку. Нужна параллельность — пишите process с code::wait.

Строки кода и жизнь потоков ​

Строка кода — одно событие, функция или процесс целиком (в мире кода это ряд блоков). Поток — один запуск: событие сработало, процесс стартовал. От этих двух понятий зависит, что переживёт выход игрока, ошибку и перезаливку.

Ошибка обрывает строку ​

Ошибка сервера останавливает остаток своей строки: действия после неё, repeat::forever дальше в этой строке и всё в вызванных функциях. Другие события и процессы работают дальше.

Отсюда правило для верхнего кода: весь world_start — одна строка. Долгий мировой цикл ставьте последним, а перед ним — только простую настройку переменных. Или выносите цикл в свой процесс NO_TARGET.

Поток умирает вместе с целью ​

Поток, привязанный к игроку или сущности, обрывается на ходу, когда цель исчезает: игрок вышел, моб умер.

  • repeat::forever в player_join — цикл одного игрока, кончится с его выходом.
  • Процесс, запущенный name() из события игрока, тоже умрёт вместе с ним.
  • player_quit тоже может не доиграть до конца. Не полагайтесь на него в важном: мировой цикл раунда каждый тик сверяет список живых с value::all_players_names.
  • Исключение: поток entity_death живёт и после code::wait (сущность уже мертва, код идёт дальше).

Повторный /play — два цикла ​

Если ввести /play, когда мир уже в игре, player_join сработает снова, а старый цикл игрока продолжит работать. Два цикла — двойные монеты и тики. world_start при этом не повторяется. Защита — поколение (проверено на сервере):

jc
game var %player%_loop

event<player_join> {
  %player%_loop = value::timestamp
  line var my = %player%_loop
  repeat::forever() {
    code::wait(1, time_unit = "SECONDS")
    if (%player%_loop != my) { code::stop_repeat() }   // новый вход забрал цикл
    player::action_bar("&7Ты в игре")
  }
}

/build и деплой ​

  • /build (и jmvcc client deploy) убивает все идущие процессы и циклы сразу, без единого шага после.
  • Порядок остановки: сначала player_quit для каждого игрока (он ещё в value::players), потом в тот же тикworld_stop, где игроков уже 0: select::all_players никого не найдёт, %player% не подставится.
  • world_stop выполняется синхронно в момент остановки: короткая работа успевает (20 000 шагов цикла прошли, запись в save var сохранилась), но код после code::wait не выполнится никогда.

Итог: сохранение по игроку — в player_quit, общее для мира — в world_stop, и без ожиданий.

jc
save var %player%_best
save var total_rounds
game var %player%_score
game var rounds = 0

event<player_quit> {
  if (%player%_score > %player%_best) { %player%_best = %player%_score }
}

event<world_stop> {
  total_rounds += rounds                // никаких code::wait: после него ничего не выполнится
}

Чтобы деплой не срывал матч или крафт с ожиданием, есть мягкая остановка: std::session и event<jmvcc_stop>. Подробно — в Мягкой остановке.
