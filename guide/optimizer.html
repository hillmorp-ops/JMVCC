Оптимизатор -O ​

Флаг -O сжимает скомпилированный модуль: блоков становится меньше, а сервер выполняет столько же действий или меньше на любом пути. Это главное правило: приём, который экономит блоки, но нагружает сервер, в оптимизатор не попадает.

text
jmvcc compile main.jc -O
jmvcc check main.jc -O
jmvcc trace main.jc -O            # посмотреть, во что сжалось
jmvcc client deploy main.jc -O    # залить в мир через мод

Без -O компилятор выдаёт тот же JSON, что и раньше, байт в байт. Оптимизатор работает только под флагом.

Что получается ​

Возьмём обычный код с ==, || и функцией:

jc
game var %player%_lvl
game var %player%_hits

function bonus(n) {
  if (n > 10) {
    return 5
  }
  return 1
}

event<player_join> {
  %player%_lvl ??= 1
  %player%_hits = 0
}

event<player_left_click> {
  %player%_hits += 1
  if (%player%_hits == 10) {
    %player%_hits = 0
    %player%_lvl += bonus(%player%_lvl)
  }
  if (%player%_lvl == 1 || %player%_lvl == 2 || %player%_lvl == 3) {
    player::action_bar("&aНовичок: удар ${%player%_hits} из 10")
  }
}

jmvcc trace показывает, сколько блоков в каждом обработчике:

text

event<player_join> 4 блоков

    set_variable_value(variable=jmcc.1, value=1)
  }
  if_variable_equals(value=jmcc.1, compare=[0], compare_type=ANY) {
    if_variable_equals(value=game:%player%_lvl, compare=[2], compare_type=ANY) {
  ...

  set_variable_increment(variable=game:%player%_hits, number=1)
  if_variable_number_in_range(value=game:%player%_hits, min=10, max=10, including=INCLUDE_ALL) {
    ...

36 блоков стали 20. Цепочка || из трёх == превратилась в одно equals со списком, hits == 10 — в дешёвый number_in_range, лишний return в конце функции и временная переменная для результата исчезли.

На корпусе рецептов и тестовых программ -O даёт 1895 → 1722 блока (около −9%).

Проходы ​

Оптимизатор — набор проходов по уже собранным блокам. Каждый срабатывает только там, где точно не меняет смысл; если сомневается, оставляет как есть.

ПроходЧто делает
A1guard на верхнем уровне: if (C) { return } + остальное → not if (C) { остальное }
A2убирает копию параметра назад после вызова, если функция его не меняет
A3jmcc.N = jmcc.return склеивается с местом, где результат используют
A4|| с флагом: guard'ы или отрицание того же блока вместо временной переменной
A5return в самом конце функции (и так ничего не выполнится)
A6line var, которая только передаёт значение в параметр, — сразу в параметр
A7игровое значение прямо в аргумент действия, без временной переменной
B1x == a || x == b → equals(x, [a, b], ANY); x != a && x != b → not_equals со списком
B2x >= a && x < b → number_in_range; пары сравнений → multiple_equals
B3value::x во временной → %val(...) прямо в тексте или %math (только проверенные id)
B4длина и элемент списка, значение словаря → %length / %index / %entry в тексте
B5проверки списков через временную → нативное условие
B6x == 5 / x != 5 → number_in_range, если в x бывают только числа

Проходы группы B опираются на факты, проверенные на сервере (как сервер сравнивает -0 и 0, 0.1 + 0.2 и 0.3, неприсвоенную переменную и 0). Например, B6 не трогает save var и переменную, в которую где-то пишется текст: number_in_range читает текст "5" как число, а == — нет.

Как это проверено
  • Эталонный интерпретатор JSON (src/__tests__/interp.ts) гоняет каждый обработчик корпуса с разными начальными состояниями и случайными цепочками событий. Состояние, журнал действий и результаты функций с -O и без должны совпасть, а -O ни на одном прогоне не должен выполнить больше действий.
  • Мутант-тест: если из кода выкинуть действие, интерпретатор это ловит.
  • Вживую через мост: рецепты и тестовые игры залиты с -O, сервер принял, ошибок кода нет; сравнения после B6 проверены на сервере.

Когда включать ​

  • Для заливки в мир — всегда. Сервер делает меньше работы, смысл тот же.
  • Когда разбираешься, во что скомпилировалась строка, — без -O. Листинг trace без флага один в один повторяет исходник, его проще читать. Потом сравни с trace -O.
  • Ошибка сервера указывает координаты блока. С -O блоки сдвигаются, так что сверяй с тем, что реально залито.
  • Декомпилятор понимает модули, собранные и с -O, и без.

TIP

Оптимизатор не меняет алгоритм. Цикл по всем сущностям каждый тик останется циклом по всем сущностям. Дешёвый код пишется руками, -O только подчищает за компилятором.

Цена действий ​

Сервер считает нагрузку мира в value::cpu_usage (проценты). Цены ниже замерены на сервере и даны в «простых действиях»: a = i = 1, это около 0.7 мкс.

ДействиеЦена
a = i, a += 1, запись и чтение любой переменной≈1 (line / game / save var стоят одинаково)
if (x > 6), <, >=, <=≈1
variable::number_in_range(x, 6, 6, "INCLUDE_ALL") (то есть x == 6 для чисел)≈1.5
if (x == 6), !=, сравнение текстов≈8
l[i] / l[i] = v≈1 / ≈1.5 (размер списка не важен)
m[k] / m[k] = v≈1.2 / ≈1.8
append≈7.5 (несколько значений — одним append([a, b]))
l.index_of(x) / l.contains(x)≈2.6 / ≈9
"$a$b" / variable::set_text([..])≈2 / ≈7
выражение %math (a * 2 + 1)≈3
вызов функции / с аргументами и return≈2 / ещё ≈+7
start_process≈4
итерация times / on_range / for_each≈0.5
итерация repeat::while со счётчиком≈1.8
частица / action bar / звук или title (один игрок)≈17 / ≈8 / ≈3
сортировка 50 чисел≈67

Главное, что отсюда следует:

  • == и != — самые дорогие условия. Числа в горячих циклах сравнивай через < >. Несколько значений сразу — variable::equals(x, [1, 2, 3], compare_type = "ANY"): одно условие вместо трёх.
  • Выбор по ключу — индексом, а не цепочкой if (k == ...): список LV[k], словарь M[k] или code::call_function(LF[k]). Цепочка из 10 веток стоит около 46 на ключ.
  • Функция в цикле на сотни итераций за тик — встрой её код или вызывай без аргументов через общие переменные.
  • Чтение большого списка копирует его (≈0.25 мкс на элемент): не вытаскивай большие списки каждый тик.
  • Спящий процесс бесплатен, каждое пробуждение — около 6 мкс. Где не нужен каждый тик, ставь wait(5) или wait(20).

Так выглядит дешёвый мировой цикл:

jc
game var hp = 100
game var phase = 0
game var PHASE_TEXT = ["&aспокоен", "&eзол", "&cв ярости"]

event<world_start> {
  repeat::forever() {
    // < и > по ≈1, а не == по ≈8
    if (hp < 30) {
      phase = 2
    } else if (hp < 70) {
      phase = 1
    } else {
      phase = 0
    }
    // текст по ключу — элемент списка, без цепочки if (phase == ...)
    player::action_bar<all_players>("Босс ${PHASE_TEXT[phase]}")
    code::wait(5)
  }
}

Бюджет CPU ​

  • Держи тяжёлый код в пределах ~3 мс за тик, пики — не выше ~80% value::cpu_usage.
  • Около 100% на мгновение терпимо. Долго выше 100% — мир падает с ошибкой high_cpu.
  • 1% CPU — это примерно 68–125 мкс кода за тик, множитель плавает между сессиями. Меряй на месте: читай value::cpu_usage раз в секунду, а не в цикле каждый тик.
  • Красота не должна стоить CPU: частицы и звуки — на событиях и понемногу, без циклов «каждый тик».

Тяжёлые места

  • Процесс на каждый движущийся объект с select по имени внутри цикла — это O(N²) поисков сущностей. Держи позиции в словаре и крути один цикл.
  • world::set_block для часто меняемых блоков — с update_blocks = true: так в ≈2.5 раза дешевле, и клиент видит изменения из мирового цикла.
  • clone_region из других чанков стоит +≈5 мс за вызов при любом размере. Держи шаблоны над или под ареной, в тех же чанках. Не больше 1–2 клонов за тик.

Подробные замеры (дисплеи, постройка карт, лимиты за тик) — в llms.txt, раздел про цену кода. Частые ошибки — в граблях.
