RPC агента ​

Проверено на сервере

RPC проверен вживую (server-check-27, 2026-11-04): вызовы с аргументами и возвратом, get / set, code::wait внутри rpc-функции, ключ машины, отказ без --rpc.

Зачем ​

Обычно агент может только водить игрока и перезаливать код. При перезаливке теряется всё состояние: раунд, счёт, расставленные мобы. RPC даёт агенту вызывать функции и читать или менять переменные кода, который уже работает в мире, без передеплоя. Получается REPL и отладчик в одном: «выдай мне 100 монет», «какая сейчас фаза», «запусти раунд».

Что пометить в коде ​

Слово rpc ставится перед function и перед game var / save var с простым именем. Только помеченное доступно агенту:

jc
rpc game var coins = 0

rpc function give(n, extra = 1) {
  coins += n + extra
  return coins
}

event<player_join> {
  give(1)
}

rpc function — обычная функция: код зовёт её как всегда. rpc на process не ставится: процесс запускают из rpc-функции.

jc
rpc game var phase = "lobby"

process round_loop() {
  phase = "game"
  code::wait(30, time_unit = "SECONDS")
  phase = "lobby"
}

rpc function start_round() {
  code::start_process("round_loop")
  return phase
}

Как звать ​

Сначала залей код с флагом --rpc. Это dev-сборка: компилятор добавит приёмник.

bash
jmvcc client deploy main.jc --rpc   # без --rpc слово rpc ничего не меняет
jmvcc client rpc-list               # что доступно: function give(n, extra?) → значение / game var coins
jmvcc client call give 5            # → 6 (результат печатается как JSON; null, если return нет)
jmvcc client call greet Steve '[1,2]' '"5"'   # аргумент — JSON, если разбирается, иначе текст
jmvcc client call give -- -5        # отрицательные числа — после --
jmvcc client get coins              # → 6
jmvcc client set coins 100          # → 100

У всех команд есть --timeout <с> (по умолчанию 5). compile, check и trace тоже понимают --rpc: например, jmvcc trace main.jc --rpc покажет, во что собрался приёмник.

Релиз — без флага

Без --rpc модуль собирается точно так же, как без слова rpc: тот же JSON, приёмника нет. Отлаживаешь — заливай с --rpc, отдаёшь игру — без него.

Как это работает ​

  • Функция выполняется в потоке владельца мира: цель — владелец, player::message придёт ему. Аргументы передаются по порядку, недостающие берутся из значений по умолчанию.
  • Функция делит var с вызывающим, как любой вызов. code::wait внутри можно: ответ придёт, когда функция вернётся (следи за --timeout).
  • Значения идут через variable::parse_json / variable::to_json. Числа, текст, списки и словари (JSON-объекты) работают.

Ошибки (exit 1) выглядят так: unknown function f, give takes 1..2 arguments (n, extra), got 3, unknown variable x, set needs value.

Если ответа нет («нет ответа», exit 1), причин может быть несколько:

  • мир залит без --rpc;
  • такой rpc-функции или переменной нет;
  • в игре сидишь не ты-владелец, а другой игрок;
  • ошибка сервера оборвала строку — смотри jmvcc client logs --errors;
  • функция завершила поток (code::end_thread, break вне цикла).

Транспорт ​

Чата и окон RPC не использует. CLI шлёт через мост пакет custom click jmvcc:rpc с SNBT-данными, например {id:"<id>", op:"call", fn:"give", args:"[5]"}. Есть ещё op:"get", op:"set" и op:"list". Код мира отвечает строкой log только тому, кто спросил: jmvcc:rpc <id> ok [<json>] или jmvcc:rpc <id> error <текст>. Мост читает ответ из журнала, а в чате строки jmvcc:* не показывает.

Приёмник делит одно событие player_custom_click с мягкой остановкой. Твои собственные обработчики player_custom_click работают как раньше и ключей jmvcc:* не видят. На тик RPC ничего не тратит: одно сравнение ключа на каждый пакет custom click.

Безопасность ​

  • Только владелец мира. Приёмник выполняет пакет, только если отправитель — владелец (%uuid% равен value::owner_uuid и есть право OWNER). Пакеты от остальных молча отбрасываются.
  • Только помеченное. Доступны лишь имена с rpc. Компилятор собирает их в цепочку проверок, вызова функции по произвольному тексту нет.
  • Только в dev-сборке. Без --rpc приёмника в модуле нет.
  • Как любая операция моста. Каждый вызов меняет игру, поэтому подчиняется /j remote off и показывает игроку title «Агент работает» (если не открыта серия jmvcc client control begin). Подробнее — Мод JMVCC Bridge.

Значения и подводные камни ​

Проверено на сервере (server-check-27):

  • Ключ машины. Каждый запрос несёт ключ из ~/.jmvcc/rpc-key. Ключ создаётся при первой сборке с --rpc и вшивается в приёмник. Если владелец кликнет по чужому тексту с custom click, запрос уйдёт без ключа и ничего не вызовет. Ответ error bad key значит, что мир залит с другой машины или ключ сменился: перезалей с --rpc с той же машины, с которой вызываешь.
  • Числа возвращаются дробными (6.0), CLI печатает 6. Тексты, списки (вложенные тоже) и словари доходят как есть. JSON true становится текстом "true". Локация приходит Java-строкой "Location{world=...,x=0.5,...}": если нужны координаты, верни [loc.x, loc.y, loc.z].
  • %плейсхолдеры% в тексте сервер подставляет при каждом использовании. set сохранит %player% как есть (CLI шлёт % как %), но get вернёт уже ник.
  • PowerShell 5.1 выкидывает кавычки " внутри аргументов: '[1,"a"]' доходит как [1,a]. Такой аргумент CLI отвергает с ошибкой. Пиши \", передавай аргументы файлом --file args.json или запускай из Git Bash. Отрицательные числа ставь после --: jmvcc client call give -- -5.
  • Нет ответа (exit 1): мир залит без --rpc, такой rpc нет, ты не владелец, строку оборвала ошибка сервера (jmvcc client logs --errors) или функция завершила поток.
